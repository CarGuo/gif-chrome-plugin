# 0.1.8：下载档位与完整选区修复

## 根因与修复

用户在 X 的默认完整选区、5×、4 MB、800 px、10 fps 设置下，下载后收到 `Choose a valid start and end within the media duration.`。

实际网页 MSE 播放器显示 127.893333 秒，下载文件的视频轨为 127.85 秒。0.1.7 把网页时长保存为一个固定结束时间，下载成功后再拿它与文件时长比较，于是完整选区反而越界。修复没有增加容差、校准两个时钟或填充尾帧：默认选区保存 `endMode: source`，下载后取真实文件结尾；手动结束时间为 `endMode: time`，不自动缩短。实际文件同时提供处理宽高和全片帧数预算。旧完整任务在输入边界迁移，重新编辑时保留完整 / 手动选区意图。

另一处问题是 X 下载固定选择最高码率，通用多档选择还把最长边当成了要达到的最低清晰度。现在统一选择最长边不超过设置上限的最大档，适用于横屏和竖屏；如果全部档位都超限，只能取最小原档后缩小。单一直链无法在下载之前凭空变出较小源文件。后续处理不放大视频。

X 的各档尺寸按公开 URL 的尺寸字段读取，与 [yt-dlp 的 Twitter extractor](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/twitter.py) 使用的方法一致，不把页面尺寸当作下载档位尺寸。帖子与唯一封面匹配负责身份校验，网页时长不再被误用为媒体身份。

## 回归方法与边界

- `npm run check` 通过：类型检查、72 项单元 / 契约测试与生产构建；`test:e2e`、`test:drop-frames` 和 `test:transports` 全部通过。侧栏按钮提交的 MSE 完整选区输出为 1.5 秒，显式选区、动画、透明合成、队列与取消均保持有效。
- `test:transports` 的真实 MSE 夹具声明 3.08 秒播放时长，完整源文件为 3 秒。修改前在 0.1.7 下载成功后触发 `invalidSegment`；修改后 2× 输出完整 1.5 秒。HLS 和真实侧栏按钮提交的文件下载均覆盖，其他手动截取保持 0.5–2.5 秒。
- 单元契约覆盖源文件比网页短 / 长、旧完整任务、只改开始时间、手动越界不钳制、实际文件决定 600 帧上限，以及请求尺寸上限贯通下载器。
- 不增加依赖或权限，不修改既有压缩顺序。

本轮仍未完成用户日常 Chrome 已安装扩展的重载与原生 X 侧栏验收；上述真实 CDN 测试使用独立受控页面，边界明确。YouTube 有效会话完整下载、Shorts 和 OpenAI 原页面的权限流程沿用 [0.1.7 尚未验收项](MEDIA-0.1.7.md)，本轮未扩展修复。代码与 0.1.8 包未提交、推送或发布。
