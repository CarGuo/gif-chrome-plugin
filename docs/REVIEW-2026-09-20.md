## 一、优先处理（高 / 中，集中在"信任边界、超时、批量保存"三处）

### 1.【安全·中】网页可伪造视频源，骗扩展带着登录凭证发请求

- 位置：[page-media.ts#L13-L66](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/page-media.ts#L13-L66)（`installPageObserver` / `readPageMedia`）；消费侧 [media-resource.ts#L19-L40](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/media-resource.ts#L19-L40)；请求发出侧 [download.ts#L19](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/download.ts#L19)
- 来源：第二轮
- 问题：扩展为发现视频源，把监听结果挂在页面可读写的 `window.__gifToolkitMedia` 上。`installPageObserver` 发现该对象已存在就直接信任并返回；即便扩展先创建，页面之后仍可改写其中的 `resources` / `sabr`。恶意页面可预置一个伪造的 m3u8/mpd 地址，当页面只有一个 `<video>` 时该地址会被自动选中；用户授权后，扩展以 `credentials: 'include'` 请求该地址（可指向第三方或内网）。
- 影响边界（不夸大）：只能"让浏览器发出一个带 cookie 的 GET 请求"，**页面读不到返回内容、数据不会外泄**（扩展无回传通道）；`file:` 不可达。
- 建议：监听状态从 `window` 移到网页碰不到的闭包内持有，`installPageObserver` 不做"存在即信任"；`readPageMedia` 只输出扩展真正监听到、带内部可信标记的来源；非页面同源、非 `<source>` 声明的 m3u8/mpd 不自动单选，要求用户确认 URL；跨域分段按目标 origin 收敛权限，不一次授予 `http*/*`。
- 置信度：0.83（链路完整；需用户多步授权，且为盲利用）

### 2.【可靠·高】解码 Worker 的请求没有超时，单项卡死会永久堵死整个队列

- 位置：[worker-client.ts#L22-L26](file:///Users/guoshuyu/workspace/gif-plugin/src/worker-client.ts#L22-L26)；调用点 [offscreen.ts#L81](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L81)、[#L99-L120](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L99-L120)；常量定义却无人使用：[model.ts#L10](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/model.ts#L10)（`seekTimeoutMs: 15000`）
- 来源：第二轮
- 问题：ffmpeg、gifsicle 都有 90 秒超时，唯独 Worker 的 `open` / `prepare` / `frame` 三类请求只有等待、没有超时。WebCodecs 对异常时间戳停滞、某帧解码或 PNG 编码不返回、Worker 内部异常不回消息时，任务永久挂起，后续排队任务全部饿死，该槽位也永久占用 24 个任务名额。
- 建议：给 `WorkerClient.request` 加可配置超时（frame/prepare 用 `seekTimeoutMs`，open 用更宽值），超时后关闭并重建 Worker、按 `seekFailed` / `encodingFailed` 结束任务。
- 置信度：高（超时缺失确定；触发概率中）

### 3.【批量保存·中】一个非法名字会让整批一个都存不了

- 位置：[background.ts#L182-L193](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L182-L193)
- 来源：**两轮均提出**
- 问题：所有标题在循环开始前统一校验，只要有一个空名/超长，整批被拒，`started` / `failed` 都不返回。但该功能自身设计是"逐项 try/catch、谁失败报谁"，旧版"保存全部"也是单项失败不影响其他，属于改完反而收紧了回退路径。
- 建议：标题校验下沉到循环内逐项处理，非法项计入 `failed`，其余正常启动。
- 置信度：中

### 4.【批量保存·中】批次可被"历史裁剪 / 清空历史"打断，违背项目明文约定

- 位置：批次循环 [background.ts#L189-L193](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L189-L193)、逐项校验 [background.ts#L27-L35](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L27-L35)；触发源：任务结束裁剪 [offscreen.ts#L251](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L251)、[storage.ts#L124-L127](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/storage.ts#L124-L127)，以及他面板清空历史 [storage.ts#L72-L103](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/storage.ts#L72-L103)
- 来源：第二轮
- 问题：批次是"id/title 快照 + 逐项现取"。批次进行中若有任务完成触发"历史超过 30 个自动裁剪"，或另一面板清空历史，名单中尚未轮到的 id 被删除，处理时 `getJob` 取不到，批次表现为部分失败。这与约定"面板关闭也不可中断已提交批次"冲突——面板关了不中断，但清理能中断；租约设计只保护已交给 Chrome 的下载，保护不到未开始项。
- 建议：批次提交时在单一事务内一次性校验全部 id 均存在且为完成态，并为整批持有结果（或批量预建 result-url 租约、结束统一释放）；校验失败的项在开始前归入 failed，处理期间不再受裁剪影响。
- 置信度：中

### 5.【批量保存·中】失败提示既不知道"是谁失败"，又把下载问题误报成"编码失败"

- 位置：提示拼装 [main.tsx#L176-L181](file:///Users/guoshuyu/workspace/gif-plugin/src/ui/main.tsx#L176-L181)；错误码兜底 [model.ts#L48-L53](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/model.ts#L48-L53)；下载接口抛错未包装 [background.ts#L42-L44](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L42-L44)
- 来源：**两轮均提出**
- 问题：① 失败提示只有去重后的错误原因，不带素材名/id，多项失败时分不清是谁；② `chrome.downloads.download` 的拒绝（目录不可写、用户在另存框取消、文件名非法等普通 Error）经 `errorCode()` 兜底报成 `encodingFailed`，而此时 GIF 早已编码完成；已定义的 `downloadFailed` 码实际上永远不会由下载路径产生。单下载路径在 0.1.9 已存在此问题，批量部分失败会集中放大它。
- 建议：下载接口调用 catch 中包装为 `new TaskError('downloadFailed')`；失败原因中带上失败项名称（或逐条"名称：原因"列出）。
- 置信度：中

### 6.【批量保存·中】在途下载并行钉住内存，最坏可达 GB 级

- 位置：[background.ts#L36-L44](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L36-L44)、[#L189-L192](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L189-L192)
- 来源：第二轮
- 问题：循环只在"交接"环节串行，Chrome 下载实际并行进行。每个 blob URL 把从 IndexedDB 读出的完整 GIF 钉在 offscreen 内存，直到下载完成才释放。最坏 30 个在途可占 GB 级，offscreen 崩溃则整批失败。
- 建议：用信号量限制在途下载数（2~4 个）。
- 置信度：中高

### 7.【批量保存·中】循环内各项无超时，且 service worker 重启后漏掉 blob 回收

- 位置：[background.ts#L108-L113](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L108-L113)、[#L189-L192](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L189-L192)
- 来源：**两轮均提出**（卡死点），重启漏回收为第二轮新增
- 问题：① `chrome.downloads.download`、`downloads.search`、两次 processor 消息均无超时，单项悬挂则后续永不启动；MV3 service worker 有 5 分钟硬上限，可能打断整批；② SW 被回收重启后 `onChanged` 只监听新事件，不对重启前已 in_progress 的下载做对账，错过事件的 blob URL 永不释放（直到 offscreen 关闭）。
- 建议：每项加超时，失败即释放并继续；SW 启动时 `downloads.search({ state: 'in_progress' })` 对账本扩展 blob 前缀的 URL。
- 置信度：卡死中；漏窗确定存在但窗口小

### 8.【命名·中】素材命名有两套编号逻辑叠加，结果依赖 frame 边界和扫描时机

- 位置：[content.ts#L51](file:///Users/guoshuyu/workspace/gif-plugin/src/content.ts#L51)（扫描时调 `mediaTitle(el, result.length)`）、[media-title.ts#L25](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/media-title.ts#L25)（单 frame 内已带序号）、[sources.ts#L32-L45](file:///Users/guoshuyu/workspace/gif-plugin/src/shared/sources.ts#L32-L45)（跨 frame 合并后再编号，调用点 [background.ts#L56-L58](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L56-L58)）
- 来源：第二轮（第一轮的第 9 条编号漂移与此同源）
- 问题：`mediaTitle` 已对未命名素材按单 frame 次序编一次号，跨 frame 合并后 `distinctSourceTitles` 用不同规则再编一次，可能叠出"素材 01 · 主机 · 素材 3"这类名字。编号按每次扫描顺序现算，懒加载/就绪时机导致视频分批出现时，同一未改名素材的编号会变，进而使默认输出名、文件名前缀不稳定。元素级 UUID 稳定，不影响身份判定。
- 建议：`mediaTitle` 不接 index、只产出无序号基础名；所有编号（含未命名占位）统一在 `distinctSourceTitles` 做一次，按稳定身份（source.id）记忆上轮映射、仅对新源追加编号。
- 置信度：中

### 9.【inspect-image·中】探测下载的 source 无校验，且全程不可取消

- 位置：转发不校验 [background.ts#L151-L158](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L151-L158)；下载不可取消 [offscreen.ts#L299-L303](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L299-L303)
- 来源：第二轮
- 问题：`inspect-image` 对 `message.source` 不做字段校验直接转发；offscreen 侧新建的 `AbortController` 从不调用 abort。面板关闭、重新扫描、切走来源都无法中止这次探测，仍会对原站发起完整请求并持有数据，与"读取动图应轻量可弃"的预期不符。
- 建议：background 复用 enqueue 的 source 基本校验；offscreen 让 controller 与请求生命周期绑定，新 scan 到来时 abort 旧请求。
- 置信度：中

## 二、计算性能（中 / 低）

### 10.【性能·中】最坏约 7 轮渲染，每轮全部帧重算，且无任务总时限

- 位置：自适应循环 [offscreen.ts#L199-L236](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L199-L236)；编码 [offscreen.ts#L138-L159](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L138-L159)
- 问题：缩尺寸最多 3 轮 + 质量地板 1 轮 + 降帧最多 2 轮，显式丢帧还额外加一整轮；每轮对全部 ≤600 帧重跑调色板生成 + 编码（单线程 WASM），丢帧模式还要先做一次全帧 framehash。源压缩率差、接近预算边界时理论耗时可达数十分钟，队列被长期独占，SW/offscreen 被回收风险升高。
- 建议：显式丢帧时按 (宽,高,fps) 缓存复用帧哈希；已达标层级的 lossy 增量续做而非每次从原始字节全量重优化；增加任务级总预算，累计耗时超限时转 `budgetUnreachable`。
- 置信度：高（计算量确定；是否不可接受取决于机型）

### 11.【性能·低】gifsicle Worker 每次调用都冷启动

- 位置：[worker-client.ts#L36-L56](file:///Users/guoshuyu/workspace/gif-plugin/src/worker-client.ts#L36-L56)；频次见 [offscreen.ts#L160-L178](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L160-L178)
- 问题：探针和每轮渲染的每次优化尝试都新建 Worker、重新加载 wasm，单任务最多约 20 次实例化/销毁。
- 建议：任务内复用一个持久 gifsicle Worker（命令带序号），任务结束再 terminate。
- 置信度：高

### 12.【可靠·低】ffmpeg 虚拟文件系统在异常路径清理不完整

- 位置：[offscreen.ts#L142-L146](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L142-L146)（frames.sha256 删除不在 finally）、[#L154-L155](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L154-L155)（output.gif / palette.png 同理）、[#L95-L98](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L95-L98)（clearFrames 单文件抛错会中断循环）
- 问题：仅拉长异常作业的内存峰值，或把可恢复错误升级为作业失败；因作业结束统一 terminate，**不跨作业、不跨缩尺寸迭代累积**。
- 建议：中间文件改 try/finally 删除；clearFrames 对单文件删除 catch 后继续。
- 置信度：高（路径存在）/ 影响低

### 13.【可靠·低】进度写库串行链：一次写失败可能污染后续

- 位置：[offscreen.ts#L121-L135](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L121-L135)
- 问题：链上某次 update 抛错会产生未处理 rejection；IndexedDB 事务理论悬挂时 `await progressWrites` 无超时。
- 建议：链尾 `.catch(() => {})`，写失败不传播到 exec。
- 置信度：中

### 14.【性能·低】成品写库前额外整份拷贝

- 位置：[offscreen.ts#L241](file:///Users/guoshuyu/workspace/gif-plugin/src/offscreen.ts#L241)（`slice().buffer`）
- 问题：成品 GIF 在写入 IndexedDB 前再复制一次，大文件时内存峰值明显。
- 建议：直接用已有的字节缓冲写库，避免二次拷贝。
- 置信度：高 / 影响低

### 15.【性能·低】React 渲染热路径有小额浪费（实际可忽略）

- 位置：[main.tsx#L162](file:///Users/guoshuyu/workspace/gif-plugin/src/ui/main.tsx#L162)（readyRevision 每次渲染重算）、[#L54](file:///Users/guoshuyu/workspace/gif-plugin/src/ui/main.tsx#L54)（进度更新新建数组+排序）、[#L159-L160](file:///Users/guoshuyu/workspace/gif-plugin/src/ui/main.tsx#L159-L160)（击键触发全量重算）

- 置信度：高

## 三、工程质量与测试（中 / 低）

### 16.【测试·高】批量保存的输入校验各拒绝分支零覆盖，且无法单测

- 位置：[background.ts#L179-L187](file:///Users/guoshuyu/workspace/gif-plugin/src/background.ts#L179-L187)
- 来源：**两轮均提出**
- 问题：非数组、空数组、超 30 条、id 非字符串/为空、重复 id、title 非法这些校验都埋在依赖 `chrome.*` 的 service worker 里，vitest 无法加载；浏览器脚本 [results.mjs](file:///Users/guoshuyu/workspace/gif-plugin/scripts/results.mjs) 只走了"全部合法"和"一条已被清理（业务失败）"，四个"拒绝整批"分支从未执行。重复 id 防线可被静默删掉而所有测试仍绿。对比 enqueue 容量拒绝至少在 e2e 中被真实触发。
- 建议：把校验抽成纯函数（如 `normalizeDownloadSelection(items, limit)`），表驱动单测覆盖全部拒绝分支；浏览器脚本保留端到端验证。
- 置信度：高

### 17.【测试·高】CI 的"8 组浏览器真实 Chrome 回归"实际跑的是 Chromium

- 位置：[ci.yml#L59-L75](file:///Users/guoshuyu/workspace/gif-plugin/.github/workflows/ci.yml#L59-L75)；默认值与分支 [results.mjs#L29-L44](file:///Users/guoshuyu/workspace/gif-plugin/scripts/results.mjs#L29-L44)；e2e 硬编码 [e2e.mjs#L38](file:///Users/guoshuyu/workspace/gif-plugin/scripts/e2e.mjs#L38)
- 问题：各脚本未设 `TEST_BROWSER`，默认走 Playwright 下载的 Chromium + `--load-extension`；只有 `TEST_BROWSER=chrome` 才走真实 Chrome 的 CDP 加载路径。Chromium 与品牌 Chrome 在扩展校验、下载文件名裁定、侧栏行为上有差异，项目脚本注释自己也承认该路径会绕过真实文件名判定。
- 建议：CI 中至少 results、download-smoke 两组设 `TEST_BROWSER=chrome`（ubuntu 预装 google-chrome）；或把对外说法改为"Chromium 回归 + 本地真实 Chrome 验证"。
- 置信度：高

### 18.【测试·高】主 e2e 脚本不收集页面未捕获异常，存在"绿但有错"的缝隙

- 位置：[e2e.mjs](file:///Users/guoshuyu/workspace/gif-plugin/scripts/e2e.mjs)（对照已做对的 [drop-frames.mjs#L19](file:///Users/guoshuyu/workspace/gif-plugin/scripts/drop-frames.mjs#L19) 模式）

- 建议：所有浏览器脚本统一收集 `pageerror` 和 console error，末尾断言为空。
- 置信度：高

### 19.【测试·中】"部分失败时失败项勾选保留"这一核心 UI 行为未被断言

- 位置：[results.mjs#L137-L149](file:///Users/guoshuyu/workspace/gif-plugin/scripts/results.mjs#L137-L149)；实现 [main.tsx#L176-L180](file:///Users/guoshuyu/workspace/gif-plugin/src/ui/main.tsx#L176-L180)

## 六、共性病根与建议的修复顺序

两轮问题看似三十条，实为同一个病根的不同表现：**多数模块按"理想情况"编写，对真实环境的不确定性（网页不可信、网络会卡死、浏览器会回收上下文、用户会并发操作）缺少统一设计。**

建议不要逐条打补丁，按以下顺序从根上处理：

1. **立两条全项目通用规矩并一次铺开**：① 所有跨上下文等待（Worker / 下载 / 消息）必须有超时和失败清理；② 扩展可信状态不放在网页可触及处，只信任扩展亲眼观察到的数据。
2. **把"批量保存 + 下载 + 命名"作为一条链整体重做**（问题 1–9、16、19 基本都在这条链上）：逐项独立判定与报错（带素材名、真实原因）、限制在途数量、整批一次校验持有、命名单一来源。
3. **补测试与诚实声明**：校验纯函数化并覆盖拒绝分支、CI 切换真实 Chrome（或修正说法）、所有浏览器脚本收集页面异常。
4. 计算性能与其余低项随后处理；老平台验收缺口（登录态 X、YouTube 完整下载、Shorts）另行规划，不在本文件范围内。
