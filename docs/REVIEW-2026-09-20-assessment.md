**深度交互**

原 Review 的最后一节把来源发现、下载保存、编解码、迁移、测试覆盖统一归因为“理想情况编程”，概括过大，无法直接指导可验证的改动。更有效的次序是：

1. **恢复与退出机制**：先保证一条坏历史记录不锁死整个处理页；Worker 无响应能取消、结束任务并继续队列。对应 #21 / #2，补故障注入回归。
2. **保存生命周期**：明确单项 / 批次接受语义，统一逐项状态、错误类别、名称展示、租约和清理竞争。对应 #3–#7 / #19 / #25 / #26 / #28。限制并发与整批持有的方案必须一起评估，避免互相矛盾。
3. **来源边界与命名**：网页数据保持不可信，授权与来源身份明确；探测可取消，默认名稳定。对应 #1 / #8 / #9。发现视频来源与把已生成 GIF 保存到磁盘是两条不同链路，不宜混成一次重做。
4. **证据驱动的优化与测试补齐**：保留已有正确测试，删除误报，再补边界；性能以现有阶段指标和同素材对照决定。不要为了让 Review 全部变绿而改变用户的处理顺序、画质或错误语义。

不采用三种表面修复：仅用 Promise.race 掩盖仍在进行的底层操作、统一 catch 吞掉存储错误、反复对上一轮有损 GIF 继续压缩。它们分别会引入迟到副作用、隐藏真实失败和累积画质损失。

依据：Chrome 说明传入请求会唤醒休眠 SW，且有特定的超时条件，不能把五分钟当作所有扩展工作的统一寿命。[Service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

Blob URL 会延长数据生命周期，但 Blob 数据可由浏览器进程以内存或磁盘持有，不能用结果总字节数等同 offscreen 堆占用。[Chromium Blob 存储设计](https://github.com/chromium/chromium/blob/main/storage/browser/blob/README.md)

跨域请求必须约束不可信来源数据；闭包或“曾观察到请求”本身不能证明 URL 被用户授权用于当前素材。[Chrome 跨域请求安全说明](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)

下载开始、中断、完成和记录删除是不同事件；onErased 独立于 onChanged，回收应围绕实际下载状态设计。[Chrome Downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads)
