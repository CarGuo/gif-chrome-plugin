## 一、直接执行

### 结论

**基础生成流程已实现且通过回归，但不能说全部规划功能都已完成。** X 登录态、YouTube Shorts、跨域 iframe 仍缺真实专项验收；原片段独立预览尚未实现。文件名新要求已落实到生成、改名、历史下载和文件名预览的统一入口。

### 本次发现并修复

| 级别 | 触发与原行为 | 修复与验证 |
|---|---|---|
| P1 | 动图读取时长、选择子片段后再次扫描，时长信息丢失；生成时选区被替换为整段 | 保留同一素材身份的解码元数据，只初始化未设置的选区。真实 UI 选择两个动图片段、扫描后生成，两个范围和成品时长均保持 |
| P1 | 动画输出只有一帧时，时长检查被跳过，可能误认定严重缩短的结果为成功 | 除真正静态来源外，所有结果检查时长；单帧 0.1 秒冒充 4 秒动画的回归必须失败 |
| P2 | 同时提交多个批次，均在写入前通过队列容量检查 | 串行接收和整批事务入库；3 批各 12 项并发请求只接收 24 项，另一批返回忙碌 |
| P2 | 历史超出 30 条后删除文件，已打开的侧栏仍保留可下载卡片 | 回收事件同步移除卡片和预览；31 条旧记录加新任务后最终界面、存储均为 30 条 |
| P2 | 多个图片来源逐个解码后再申请权限，可能丢失原点击的用户操作上下文 | 点击时一次收集所需图片来源并申请权限，再开始异步解码。来源集合去重测试和浏览器图片流程通过；未获授权的新 CDN 弹窗仍需人工选择 |
| 新要求 | 文件名含中文、空格，重复生成无法按生成时间区分 | Base64url 编码、持久化毫秒时间戳、独立 UUID；实际下载文件名和字节一致性通过 |

上述修复均保留版本注释和复现测试，不通过改变压缩上限、缩短选区或放宽动画时长要求使测试通过。

### 文件命名规则

```text
Base64url(UTF-8 标题前缀)_生成时间戳_任务唯一编号.gif
```

- 时间戳使用任务创建时间的 Unix 毫秒数；重新生成会创建新任务，改名和再次保存沿用原生成时间。
- 同毫秒的多个任务由 UUID 区分；文件名不包含中文、空格、路径分隔符或 Base64 填充符。
- 长标题按完整 UTF-8 字符限制为 72 字节再编码，文件名最长约 147 字符，界面标题不截为该前缀。
- 历史任务通过同一命名函数读取和下载，不重新编码已有 GIF。
- 用户在系统保存对话框主动修改文件名、或系统对重复保存作冲突处理，属于浏览器的保存行为；以上规则约束扩展生成的文件名。

## 二、深度交互

### 完整选区不等于任意长度均可处理

当前每个任务最多采样 600 帧：默认 10 fps 时约为 60 秒成品，2× 时可覆盖约 120 秒原视频。PNG 总缓存也限制为 160 MiB。超过预算会报错，不暗中缩短。如果目标包含长视频一键转完整 GIF，需要重新设计分块取帧、缓存与编码，不应仅扩大常量。

### “抓取”目前指按时间读取播放器画面

视频没有原文件下载功能，也没有完整 HLS/DASH 下载器；使用页面已解码帧按时间取样。它可以处理正常播放的部分 Blob/MediaSource 视频，但依赖播放器能跳转、能导出像素、来源页面保持打开。GIF/WebP 则获取原始图片字节。

全页图片发现仍使用 URL 类型线索；无后缀 GIF/WebP 可通过直接右键进入字节识别，但不能据此宣称自动发现所有 Blob、CSS 背景和任意嵌套来源。

### 最后还差什么

1. **核心验收**：真实登录态 X、Shorts，以及跨域嵌入页面的来源授权和完整生成保存流程。
2. **规划功能**：原片段独立预览、真实帧缩略图。当前成品 GIF 预览已完成。
3. **性能结论**：“快速”还缺选定设备上的冷/热启动与长片段耗时基线；现有资源限制保持可见。
4. **上架工作**：图标、商店材料、许可文本及对应源码分发。当前是可加载的本地测试版，不是已提交商店的版本。

参考依据：[RFC 4648 Base64url](https://www.rfc-editor.org/rfc/rfc4648.html#section-5)、[Chrome 权限请求的用户操作要求](https://developer.chrome.com/docs/extensions/reference/api/permissions#step-3-request-optional-permissions)。
