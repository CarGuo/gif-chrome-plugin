# 0.1.7 网页视频下载验收

本次修正的是输入获取范围：插件必须先取得当前网页中所选视频的完整媒体，再进行 GIF 处理。0.1.6 只对普通直链和 X 做到了这一点；其余播放器仍使用网页跳转抓帧，不符合要求。0.1.7 删除该抓帧路径。本文记录实际验证范围，未通过的项目不能视为已经支持。

## 实现边界

- 普通视频文件：下载完整文件。文件 Blob 从所属页面异步读取。
- HLS：Mediabunny 解析 TS / fMP4 清单和分片；DASH：video.js 的 `mpd-parser` 解析 MPD 继承、时间轴及分片路径，再共用分片解复用流程。获取完整视频轨后无重编码合并为本地 MP4。
- Vimeo iframe：读取当前播放器配置所声明的 HLS 主清单，验证播放器视频 ID；没有 OpenAI 域名或示例视频 ID 的生产代码特判。
- X：按所选帖子和封面匹配公开接口中的视频，再下载 MP4。不是取页面上遇到的第一个视频请求。
- YouTube：接入 `googlevideo` 的 SABR 状态机，读取当前播放器的媒体格式及实际播放请求；播放器身份和下载分片状态分开管理。protobuf 身份字段保留原始字节，避免生成的旧 schema 丢弃新字段。必须收到视频身份匹配与完整结束信号，才交给后续转换。
- 网络、清单解析、分片合并和视频解码位于 Worker。只有文件 Blob / SABR 的所属页面网络读取及 DOM 发现需要页面环境；不在 UI 主线程编码或操作播放进度。
- 单个输入上限 128 MiB；网络超时依据 30 秒无数据活动。取消会终止当前请求及 Worker。DRM 和直播不转换成虚假的完整文件。
- 对无法明确关联的流，要求用户选择来源。同一 frame 有多个播放器时，即使只观察到一张清单，也不能擅自给所有播放器使用。

YouTube 使用公开样本 `https://www.youtube.com/watch?v=aqz-KE-bpKQ`（634.601 秒）。另外用**完全不加载插件和观察脚本**的 Chrome 152 做对照：无头和有窗口模式均在前一分钟内停止，播放器显示 “Something went wrong”，有窗口对照的播放器错误码为 `ump.spsrejectfailure`。这说明当前测试会话自身受到播放流会话拒绝，不能用该失败证明下载器已经正确，也不能把它归因于 GIF 编码慢。后续仍需在可正常持续播放的会话中完成整段下载验收。

后续在用户日常 Chrome 会话中打开同一公开样本，原生播放器正常连续播放至 3:45，随后手动暂停。因此拒绝现象局限于本次临时浏览器配置，不能表述成用户的 YouTube 也无法播放。尚未把本地 0.1.7 加载进日常 Chrome，正常会话中的扩展下载验收仍待进行；电脑操作工具要求在安装本地未上架扩展和授予站点访问权限前确认。

真实站点数据会变化。报告位于被 Git 忽略的 `test-results/platform-vimeo-verification.json`、`test-results/platform-youtube-verification.json` 和 `test-results/transports/report.json`；成功 GIF 保存在同一目录。报告不包含 SABR 请求体或播放令牌。研究过程中临时会话资料不进入发行包。

## 处理顺序与性能

完整获取媒体 → 按 speed 映射输出时间轴 → 抽样预估像素 / 帧数对应的体积 → 优先调整尺寸 → GIF 调色板与编码 → Gifsicle 优化 → 仍超限时最后降低帧数。

speed 不需要先重编码一份加速 MP4。127.85 秒按 5× 映射为 25.57 秒，10 fps 只需要 256 个输出采样点。这样保留用户要求的处理顺序，并省掉无用途的中间视频编码。调色板负责把真彩色像素映射到 GIF 的有限颜色，GIF 编码再保存这些帧；耗时取决于处理的总像素和尝试次数，不能只用输出秒数推算。

原 X 样本的同设置性能证据见 [0.1.6 性能记录](PERFORMANCE-0.1.6.md)。该记录已分别列出本地处理与真实 CDN 下载耗时，不能把约 12 秒的本地结果当成所有网站的总等待时间。

0.1.7 在 Chrome 152 的本地输入复验为 13.5046 秒，其中本地下载 0.1515 秒；输出仍为 313×195 / 256 帧 / 25.57 秒 / 3,445,103 字节，一次完整编码、三次优化，无自动降帧。实测完整调色板阶段 3.99 秒，完整 GIF 编码 1.90 秒。下载网络条件不在这组本地计时内。

复验发现首次生成与面板历史读取并发时存在处理页初始化竞态。现在把存在性检查与创建统一纳入同一个启动 Promise，所有请求共同等待初始页面加载结束。浏览器回归新增了关闭处理页后同时读取历史、提交任务的场景，防止再次将“context 已出现”误判为“可以收消息”。
